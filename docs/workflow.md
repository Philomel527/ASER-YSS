# 从剧本到 YSS 剧情代码

## 1. 资料与工具接收

先取得用户提供的完整工具包和教程内容，核对文件来源和版本。压缩包先解压到仓库外的临时位置，检查目录、隐藏文件、链接及文件大小，避免覆盖仓库的 Git 元数据和已有文件。

计划将工具包放在 `vendor/ASER/`，保留原始层级；若其说明要求固定路径，以检查结果调整。导入前检查 GitHub 文件大小限制；若存在需要 Git LFS 的文件，先确认 LFS 支持，再提交，不能仅为成功上传而静默遗漏工具文件。

检查实际编辑器、目录名单、示例和说明，记录工具文件的 SHA-256。工具包未取得前，不猜测安装方式、语法或文件扩展名。

## 2. 教程学习和工作原理核验

对照教程与实际工具确认：

- YSS 与 ASER 分别承担编辑、解析、转换、导入、播放中的哪些步骤；两者交换的文件格式是什么。
- 剧情代码文本的文件后缀、编码、换行、注释、转义和参数规则。
- 场景初始化、对话、旁白、角色显示、表情、背景、音乐、音效、等待、转场及结束的语法。
- 指令执行顺序、时间单位、并行效果以及错误报告的读取方法。
- 资源名单各字段的含义、可用标识、路径规则与版本适配方式。
- 工具运行平台、依赖、使用限制，以及在当前云环境能够验证到哪一步。

将有证据的结论和仍有疑问的部分分开记录。使用实际解析或转换功能验证最小示例；如果 ASER 需要本环境不具备的界面或平台，明确保留播放验证事项。

## 3. 用户剧本转换

用户提供剧本与创作要求后，先提取技术需求，再从当前资源名单核对素材。对不影响创作的实现细节使用已验证的工具默认值；涉及缺失素材、台词歧义或表达变化时，提出具体问题。

代码交付到 `story-code/`。该目录只放根据用户剧本编写的 YSS 剧情代码文本，不放模板占位文件、工具包原带示例和说明。

## 4. 检查与交付

按实际工具支持的能力依次检查语法、资源引用、转换结果和播放效果。记录运行命令、工具版本、结果及未执行事项。尚未验证的代码不可标成已兼容或已通过播放测试。

## 5. 更新处理

接收新编辑器或目录名单后：

1. 记录来源、版本、日期、哈希和变化说明。
2. 对比指令或参数变化，以及资源的新增、删除和重命名。
3. 单独提交工具或名单更新，保留可追溯的 Git 历史。
4. 查找已有剧情代码中受影响的引用，提出需要用户决定的素材替换。
5. 重新检查受影响文件和场景，再更新兼容性记录。

目前工具包和教程尚不可读，上述内容是项目执行流程，具体语法和命令仍待实证确认。
